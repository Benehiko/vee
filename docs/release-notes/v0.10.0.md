## Highlights

This release is about the desktop template earning its name. Before it, a
windowed desktop guest on a macOS host booted into a black or frozen window
more often than into GNOME: the bundled QEMU had no windowed OpenGL sink, the
aarch64 board shipped no input devices, the freshly installed desktop never
started its own graphical target, and a reboot inside any QEMU guest wedged
the VM until someone power-cycled it by hand. Each of those is fixed below,
and every fix was verified on a booted guest. Alongside the desktop work,
`vee cp` and `vee wait` land as commands, and "ready" now means vee can
actually log in.

**Desktop guests render on ANGLE/Metal — the bundle moves to QEMU 11.1.0
with a cocoa OpenGL patch.** The managed QEMU bundle is now
`qemu-11.1.0-vee2`, built from the 11.1.0 final release (which also brings
HVF nested virtualization for `--nested` and Apple's in-kernel vGIC on Apple
Silicon). The GL half of the bundle — ANGLE and virglrenderer — has been
linked in since the 11.1.0-rc2 bundle, but upstream's cocoa display is
2D-only, so `-display cocoa,gl=es` refused on every unpatched build and the
GL stack had no windowed sink. The vee2 bundle ships Akihiko Odaki's cocoa GL
support, ported to 11.1.0, so a windowed desktop or gaming guest renders
through virglrenderer on ANGLE's Metal backend instead of software. Verified
on an M4 Max: virglrenderer reports "ANGLE Metal Renderer: Apple M4 Max" in a
booting Ubuntu desktop guest. The patch is published as a release asset
alongside the bundle (GPLv2 §3).

**Hosts whose QEMU lacks windowed GL fall back instead of failing.** A QEMU
built without cocoa OpenGL — the Homebrew binary, or any pre-vee2 bundle —
exits instantly on the virtio GL flags the desktop path emits, so those VMs
never booted. vee now detects that startup crash and relaunches once with the
plain 2D adapter: the guest renders in software, which is fine for app
testing. The downgrade lives in a per-boot flag, never the persisted config,
so the same VM picks GL back up on its own the moment a GL-capable QEMU is in
place. Both adapters are pinned to the same 1080p EDID, so the desktop no
longer changes resolution depending on which path it landed on.

**Windowed guests accept keyboard and mouse.** The aarch64 virt board ships
no built-in input devices — unlike x86, where q35's PS/2 controller is always
there — and the virtio-gpu path attached only the GPU and display. A windowed
Linux desktop rendered fine while QEMU dropped every click and keystroke,
making the GUI look frozen on a perfectly healthy VM. Every non-headless
virtio-gpu guest now gets virtio-keyboard-pci and virtio-tablet-pci (an
absolute pointer, so the cursor lands where the host cursor is). The drivers
ship in the Linux kernel; input works on first boot with no guest-side setup.
Windows guests already wired USB input explicitly and are unaffected.

**The desktop template shows a desktop on first boot.** Four separate faults
conspired to keep the GUI invisible until a manual power-cycle, and each is
fixed:

- Provisioning set `graphical.target` as the default but never started it,
  so the finished system sat on the text console until the next boot.
  Provisioning now ends by isolating `graphical.target`, bringing GDM up in
  the same boot.
- Ubuntu 24.04.9's gdm3 package prompts about the pre-seeded autologin
  conffile, and under a noninteractive frontend that prompt aborted the
  entire desktop install — no GDM, no sshd. The install now keeps the
  pre-seeded file, which is the point of seeding it.
- Partway through the install, systemd-networkd restarts with its
  netplan-generated config gone from `/run`: the NIC keeps carrier but loses
  its address, and the guest is unreachable until a reboot. The template now
  runs `netplan apply` at the end of provisioning, handing the NIC back to a
  configured renderer in the same boot.
- The autologin session could lock itself, turning every screenshot into a
  black lock screen with nobody around to unlock it. A dconf system database
  now disables locking, idle blanking, and the lock screen, with the keys
  locked down so an in-guest settings change cannot re-enable them mid-test.

The several minutes of GNOME installation that remain after SSH comes up are
now announced rather than mistaken for a broken VM: `vee create` prints a
first-boot note pointing at `vee wait --cloud-init`, and the guest console
shows an "installing" banner until the moment the graphical session starts.

**A reboot inside a QEMU guest no longer wedges the VM.** QEMU's default
reboot action warm-resets the board in place, and under HVF the firmware
re-enters edk2 with interrupt and timer state Hypervisor.framework does not
reinitialize. The guest died with the QEMU process alive and healthy-looking,
and no layer noticed: the event watcher filtered everything but SHUTDOWN, and
the daemon's liveness check was a live PID. `vee status` sat on a stale phase
forever. The QMP owner connection now watches RESET events and answers a
guest-initiated reset with what the user previously had to do by hand: a
forced stop and a fresh start. Installer-driven reboots during an install
pass stay in place, the new "reboot" shutdown reason keeps the VM marked as
wanting to run (so a failed relaunch is retried by the daemon's autostart
pass), and `vee wait` rides out the power-cycle window instead of
misreporting the relaunched guest as exited. Alongside this, the daemon now
re-adopts unwatched VMs on every poll pass — previously a VM started by the
CLI after the daemon booted had no QMP owner once that CLI exited, so its
guest events went unseen.

**`vee cp` — copy files between host and guest.** Bidirectional
`vee cp <src> <dst>` over the system `scp`, where either side can be
`<vm>:<path>`. Endpoint resolution follows `vee backup`'s order, host keys
use the vee-managed `known_hosts` with `vee ssh`'s scrub-before-connect
posture, and Windows guest paths are normalized so drive letters work.
Exposed over MCP as `vm_cp`.

**`vee wait` — block until the guest is actually usable.** Waits for an
authenticated SSH exec round-trip — a stronger signal than a TCP accept,
which can flip before `authorized_keys` lands. `--cloud-init` additionally
waits for provisioning to finish, and now survives the mid-install SSH drops
the desktop template causes: the wait redials and re-enters on
connection-level failures, and only cloud-init reporting error status (or the
deadline) is terminal. The probe escalates through passwordless sudo where
the guest grants it — on Fedora the status file is root-readable only, so the
unprivileged probe failed hard while provisioning was fine — and guests
without cloud-init pass immediately instead of by shell accident. Exposed
over MCP as `vm_wait`.

**"Ready" at start time now means vee can log in.** For guests vee's key is
known to log into — any cloud-init-provisioned template — the start-time
readiness probe requires an authenticated SSH exec round-trip, not a bare
port-accept, which could flip ready while `vee ssh` still bounced off a
half-provisioned account. Guests without a known account (imported disks,
password-auth templates) keep the reachability floor.

### If you already use vee

- The managed QEMU upgrades itself to `qemu-11.1.0-vee2` on the next
  `vee start` — a fresh bundle download, nothing to do by hand.
- Restart the daemon after upgrading the binary: the reboot power-cycle and
  the per-poll re-adoption live in the daemon process.
- A reboot inside a QEMU guest is now answered with a forced stop and a
  fresh start rather than an in-place board reset. If something you run
  depended on the old wedge-in-place behavior, it will now see a real
  power-cycle.
- Existing desktop VMs get the input devices, the GL rendering, and the
  reboot fix on their next start — those are start-time properties. The
  first-boot fixes (graphical target, gdm3 conffile, netplan bounce, lock
  disabling, banner) are baked in at create time, so recreate the VM to get
  them.
- `vee screenshot` warns when the captured frame is a single solid color —
  a locked session's black lock screen, or a GL-backed console whose scanout
  never reaches the CPU-side surface — naming both causes instead of handing
  you a silent black PNG. The PNG is still written.
- An explicit `--virtiofs-dir` on a host without virtiofsd is refused at
  create time instead of being silently dropped at start.
- Every cloud-init `runcmd` entry is now rendered as a YAML literal block
  scalar. Previously a single-line command containing `": "` or `#` parsed
  as the wrong YAML type and killed the guest's entire provisioning stage.
