## Highlights

This release is mostly about graphics on Linux guests that run without
passthrough, plus an experimental first try at the same on Windows. The
`virtio` GPU path in the gaming templates was a fallback: Venus could only be
switched on by hand-editing YAML, guest Vulkan found no GPU, KWin froze the
first time the mouse moved over a window, and pointer-locked games ignored
the mouse. Each of those is fixed below, and each fix was checked on a
running guest. The release also adds read-only virtiofs shares, scriptable
`vee config` flags, and a NordVPN endpoint fix that lets torrent guests
follow a re-addressed server.

**Venus and the virtio-GPU settings are available on the CLI and MCP.**
`gl_backend`, `venus` and `host_mem` were on the GPU config but could only be
set by editing a VM's YAML. `vee create` now takes `--gpu-gl-backend`,
`--gpu-venus` and `--gpu-hostmem`, and the MCP create tool has the matching
`gpu_gl_backend`, `gpu_venus` and `gpu_hostmem` fields. Venus without a sized
host memory window fell back to QEMU's default, which is often too small and
fails in ways that are hard to trace, so `--gpu-venus` alone now defaults the
window to `8G`. The default is applied when the device is built, so
hand-written YAML gets it too. Combinations that would have been silently
dropped are refused at create time: the GL options outside
`--gpu-mode=virtio`, `--gpu-hostmem` without `--gpu-venus`, or an unknown GL
backend.

**Guest Vulkan works on non-passthrough gaming VMs.** The gaming-arch install
always added a udev rule that hid the virtio-gpu render node. The rule exists
for passthrough, so RADV binds to the VFIO GPU. A non-passthrough VM has no
second GPU, so the rule hid its only render node and the Vulkan loader found
nothing. The rule is now only added for passthrough. Non-passthrough installs
keep the render node usable and point the Vulkan loader at the virtio ICD.
That second step is needed because otherwise RADV takes the node first and
fails. Both rules were also being written to the live ISO's `/etc` rather
than the target root under `/mnt`, so **the passthrough rule from #46 had
never reached an installed system** until now. Checked on a Venus VM: guest
`vulkaninfo` reports "Virtio-GPU Venus (AMD Radeon RX 9070)" and `vkcube`
runs.

**KWin no longer freezes on virtio-gpu.** On non-passthrough gaming-arch VMs,
the Plasma session froze as soon as Steam, Chromium or even `glxgears` got a
mouse hover. The guest was still reachable over SSH, but the QEMU window
stopped updating. KWin 6.7 imports client shared-memory buffers through
udmabuf. The virtio-gpu driver never attaches those buffers to KWin's virgl
context, and the first use is a fatal context error in virglrenderer, after
which it refuses every further command from KWin. The virtio install now sets
`KWIN_DISABLE_UDMABUF_IMPORT=1`, so KWin uses plain texture uploads as it did
before 6.7. Passthrough installs are untouched.

**A relative pointer for pointer-locked games.** The virtio-GPU path attaches
an absolute tablet. Wayland compositors deliver absolute motion with a zero
relative delta, and a game that locks the pointer for mouse-look reads only
deltas, so the camera never moved. `--pointer mouse` (on `vee create`, on
`vee config` for existing VMs, and as `pointer` over MCP) attaches
`virtio-mouse-pci` instead. The QEMU window grabs the cursor on click and
Ctrl+Alt+G releases it. `tablet` remains the default.

**Read-only virtiofs shares.** virtiofsd has long supported `--readonly`, but
vee never passed it, so every share was read-write. `--virtiofs-readonly`
(`readonly: true` on a `virtiofs_mounts` entry, `virtiofs_readonly` over MCP)
serves a share the guest cannot write to, even as root. That suits a Steam
library or media directory the host also uses. The gaming templates pass the
setting through to their `Games` share. This also fixes a duplicate: on a
gaming template, `--virtiofs-dir` started two virtiofsd processes on the same
directory, one tagged `Games` and one tagged `share`. It now updates the
template's entry instead.

**`vee config` flags for scripting.** `--memory`, `--cpus`,
`--nic-mode`/`--nic-bridge` and the new `--cpu-pinning` skip the interactive
TUI and save straight to the VM's config, like `--ssh-port` and `--pointer`.
`--cpu-pinning` pins the VM's vCPU threads to the host CPUs you list. All of
them take effect on the next start.

**NordVPN guests can follow a re-addressed server.** The NordLynx config set
the WireGuard endpoint to the server's IP and discarded the hostname from the
same API response. The templates only install the endpoint-refresh script,
its cron entry and `crond` for hostname endpoints, so Nord guests had none of
them. When the server behind that IP was retired, the tunnel stopped passing
traffic with no way to recover. It failed closed and nothing leaked. The
endpoint is now the hostname, so Nord guests get the same refresh as any other
hostname endpoint. This is not automatic server rotation. A retired server
also means a new public key, so recreating the VM is still the fix for that
case.

**Experimental: hardware-accelerated Windows guests with WinBoat Helios.**
`--gpu-mode=helios` on the `windows` template gives the guest accelerated
graphics through the [Helios](https://github.com/winboat-org/helios)
paravirtual WDDM driver (virtio-gpu + Venus), without passthrough. vee
installs the driver unattended during provisioning, keeps an auto-logon
desktop session across reboots, and adds `vee helios status [--wait]`,
`vee helios verify`, matching MCP tools, and `vee view` support. In a live
test on Windows 11 24H2 (RX 9070), D3D11, Vulkan, OpenGL and OpenCL worked,
but **D3D12 hangs**, so D3D12-only games do not run on Helios today. Helios
needs its own QEMU fork, which vee neither ships nor builds. Build it
yourself and pass `--qemu-binary`. A Helios VM without it refuses to start
rather than falling back to the managed QEMU. See `docs/windows-helios.md`
and `docs/windows-directx-evaluation.md`.

**Smaller fixes**

- gaming-arch installs no longer abort at the services stage. A recent
  change enabled `rtkit-daemon` without installing `rtkit`, so every install
  since then failed after pacstrap and the yay build.
- `vee wait --timeout` can no longer hang forever. The SSH handshake and
  session open now have deadlines. A user-mode NAT forward accepts TCP before
  the guest's sshd is up, and a guest that rebooted mid-session left vee
  waiting with no limit.
- `vee delete` now removes boot disks moved with `--boot-disk-path`. It only
  removes a file with vee's generated name, never user files, passthrough
  devices or adopted images.
- A Claude Code skill for driving vee VMs as a test bench now ships in
  `.claude/skills/vee-vm`, and `docs/claude-skill.md` covers installing it
  for use in any project.

### If you already use vee

- Restart the daemon after upgrading the binary. A daemon running an older
  vee relaunches a Helios VM without its GPU after a guest reboot, because it
  doesn't know the new config fields.
- Existing gaming-arch VMs on `--gpu-mode=virtio` keep their old install. The
  Vulkan, KWin and rtkit fixes are applied at create time, so recreate the VM
  to get them. You can also add
  `/etc/environment.d/98-vee-kwin-udmabuf.conf` with
  `KWIN_DISABLE_UDMABUF_IMPORT=1` by hand and reboot (see the gaming-arch
  page).
- A VM config with `venus: true` and no `host_mem` now starts with
  `hostmem=8G` instead of QEMU's default.
- Existing NordVPN torrent guests keep the literal IP in their `wg0.conf`
  until they are recreated.
- `--pointer`, `--cpu-pinning` and the other `vee config` flags apply on the
  VM's next start. QEMU cannot swap input devices on a running VM.
