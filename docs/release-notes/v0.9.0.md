## Highlights

Two threads: `vee tunnel` grows into something you can leave running, and the
VPN kill-switch shipped in v0.8.0 gets hardened after running it against live
`torrent` and `bitmagnet` guests turned up several ways it could be correct in
the generated shell and still wrong on the wire. Every fix below was
reproduced on a booted VM before it was written.

**`vee tunnel --host` and `--background` — publish a service on the LAN and
keep it up across reboots.** Previously `vee tunnel` could only open a
foreground tunnel bound to loopback: it held the terminal for as long as the
service was needed, was unreachable from any other device, and was lost the
moment the host rebooted.

`--host` binds `0.0.0.0` instead of loopback, so other devices on the network
can reach the service. vee adds no authentication of its own — the guest
application's own login is the only protection once a service is published —
so the command warns and asks for confirmation before binding (`--yes` skips
the prompt for scripts). `--background` hands the tunnel to the daemon
instead of holding a terminal: it's recorded in `~/.vee/tunnels.json` and
reconciled on every daemon poll tick, so it comes up when the VM does and
survives a host reboot. A registered tunnel whose VM is stopped stays
registered but unserved rather than proxying connections it can't fulfil, and
the allocated host port (2300–2399) is persisted so bookmarks and DNS records
don't move around. `--list` reports every registered tunnel and whether it's
currently served; `--stop` removes one. SPICE can't be backgrounded — QEMU
already binds that port on the host.

HTTP tunnels published with `--host` are additionally routed by name on port
80, e.g. `http://jellyfin.benehiko-desktop/`. Routing is by virtual host
rather than path prefix, since a stripped path prefix breaks the absolute
asset URLs web UIs generate unless the app is separately configured with a
base URL — something not every app supports. vee performs the routing once a
request already carries the right `Host` header; it does not publish DNS
records for these names, since a VM manager that points its own DNS at itself
is no longer a generic tool. `docs/tunnels.md` lays out the resolution
options (a router entry, `/etc/hosts`, or a wildcard record in the
`dns-sink` template) as equals, alongside what vee does and doesn't do.

**Tunnelling into a bridged guest behind a kill-switch no longer hangs.**
`connectService` already fell back to tunnelling over SSH when a service port
was unreachable — exactly the kill-switch case — but the fallback was gated
on a recorded SSH port that bridge-mode guests never get (it exists only for
NAT hostfwd). So on precisely the VMs that needed it, vee dialled the service
port directly, the guest's firewall dropped the SYN, and the connection hung
until the client gave up rather than erroring. A bridged guest is still
reachable on 22 — the one port a kill-switch leaves open, and how `vee ssh`
already reaches it — so the tunnel now picks its SSH endpoint the same way:
prefer a recorded loopback port only if something actually answers there,
otherwise the guest's own address on 22.

**A rotating VPN endpoint no longer strands the guest.** The kill-switch pins
its WireGuard handshake hole to the endpoint's addresses, resolved once when the
template is built. Nothing recomputed them, so the day a provider re-addressed
its server the guest was stuck: `wg-quick` dialled the new IP while the firewall
still permitted only the old one. The handshake was dropped, the tunnel never
came back, and rebooting did not help — the stale addresses are what got
persisted. It failed closed, so nothing leaked, but a silent permanent outage is
the same class of failure the pinning exists to prevent.

Guests whose endpoint is a hostname now carry
`/usr/local/sbin/vee-wg-refresh-endpoint`, which re-resolves the endpoint,
re-pins the firewall, and restarts the tunnel so `wg-quick` re-reads its own
frozen peer address. On Ubuntu it runs from the existing retry timer; on Alpine
from the boot hook plus a one-minute `crond` entry, so a rotation is picked up
without a reboot. Every step fails closed: the DNS lookup opens a hole to the
configured nameservers and closes it again even on the failure path, a failed or
empty lookup leaves the existing pins untouched, new holes are installed before
superseded ones are withdrawn, and Alpine saves its rules so a re-pin survives
the next boot. An IP-literal endpoint cannot rotate and gets none of this. The
`bitmagnet` template gets the same wiring, reusing the torrent bases' scripts
rather than growing a second copy.

**IPv6 is now dropped outright.** The iptables bases installed `ip6tables` but
never gave it a rule, leaving its policy at the default `ACCEPT`. On a network
advertising IPv6 via router advertisements, a guest could reach the internet
over IPv6 on the LAN interface while every IPv4 path was correctly denied — and
an announce over IPv6 publishes your real address to the swarm just as
effectively as one over IPv4. The tunnel is IPv4-only in practice (no config
path in vee ever assigns the interface an IPv6 address), so denying the family
wholesale loses nothing and is a complete policy rather than a set of holes to
keep in sync. Loopback keeps an exception, since some software binds `::1` and
would otherwise fail in ways that look nothing like a firewall problem. The
rules are saved per-family, because Alpine's iptables service persists only the
IPv4 table — without that, the leak came back silently on the next reboot.

**qBittorrent is bound to the tunnel, underneath the kill-switch.** The
generated `qBittorrent.conf` set no interface binding, so libtorrent chose
source addresses per-route and the firewall was the only thing keeping peer
traffic inside the tunnel. The session is now bound to the VPN interface by name
— never by address, since the tunnel address rotates on reconnect — which covers
two cases the firewall alone does not: qBittorrent starting before the tunnel is
up (an unbound session announces the guest's LAN address in that window, which
is reachable in bridge mode), and Ubuntu + NordVPN, where the policy lives
inside the NordVPN daemon and dies with it. The listen port is pinned to 6881
instead of being randomised on every start, and the session no longer attempts
IPv6 announces the firewall will drop.

**The Alpine web UI works.** `--profile` names a profile *root*, not the
directory holding the `.conf` — qBittorrent appends `qBittorrent/config/` to it.
The template wrote the file one level up, where qBittorrent never looked, so it
started against an empty profile, fell back to password auth, and generated a
throwaway admin password into a log file on every start. Since no password is
provisioned, the web UI was simply unreachable: `vee tunnel` arrives on guest
loopback, exactly the case `LocalHostAuth=false` is meant to wave through, and
every request was answered `401`. The Ubuntu base was unaffected — its packaged
systemd unit locates the config via `HOME`, not `--profile`.

**qBittorrent runs in anonymous mode.** The template deliberately left it off,
on the reasoning that anonymous mode disables DHT, PeX and LSD — the peer
discovery the template is tuned for. That reasoning was stale. The conflict was
real only for qBittorrent 2.9.0 through 3.2.5, which built against libtorrent
below 1.0.0; 3.3.0 moved that behaviour to a separate "disable connections not
supported by proxies" option. On the 4.x builds every base installs from its
distro repositories, anonymous mode touches nothing but the client's own
fingerprint: a generic user-agent to trackers, no local addresses in queries to
private trackers, no configured IP reported, no client version in the peer
extension handshake, and no fingerprint in the peer ID. `AnonymousModeEnabled`
now sits alongside `DHTEnabled`, `PeXEnabled` and `LSDEnabled`, and the test
asserts all four together so a future change cannot quietly trade one for the
other. This is defence in depth, not the primary control — the interface binding
and the kill-switch cover *where* the guest is, and anonymous mode covers *what
the client looks like* to whoever is recording it.

### If you already use vee

- A daemon running from before this release predates the background-tunnel
  control-socket ops. vee detects this and reports that the daemon needs a
  restart, rather than failing with a raw protocol error.
- `site/content/commands/tunnel.md` documented a `<port>` argument and
  described `vee tunnel` as NAT-only — both stale before this release. It's
  rewritten around the real `<service>` argument and the connection path vee
  actually picks.

Existing torrent and bitmagnet VMs do not pick up the kill-switch fixes below.
They're baked into the guest at create time, so recreate the VM to get them.

- The qBittorrent web UI now binds guest loopback rather than every interface.
  It gained nothing on the wildcard — `LocalHostAuth=false` skips auth for
  loopback only, so a LAN client was answered `403` — but in bridge mode it left
  the kill-switch as the only thing between the LAN and an auth-bypassing
  listener. `vee tunnel <vm> qbittorrent` is unaffected.
- The `vee-wg-retry` timer now runs `systemctl restart` rather than `start`. The
  upstream `wg-quick@` unit is `Type=oneshot` with `RemainAfterExit=yes`, so
  systemd reported it active-exited even with the interface gone, and `start`
  returned 0 without doing anything — the timer fired every 60 seconds while the
  tunnel stayed down indefinitely.
- The Ubuntu base no longer tries to install `resolvconf`, which is not
  installable there and failed the whole package step.
- `vee network` probes a VM's VPN by mechanism rather than by provider name, so
  a NordVPN account running as NordLynx is checked as the WireGuard tunnel it
  actually is.
- New in the torrent template, opt-in: `vee create --template torrent --distro
  alpine` builds on Alpine Linux with qBittorrent under OpenRC and the
  kill-switch enforced by iptables rather than ufw. Its inbound policy is
  default-drop, and its SSH and DHCP holes are narrower than ufw's rule
  vocabulary can express. It is x86_64 only, has no SPICE display, and a NordVPN
  token is exchanged for a NordLynx WireGuard config rather than installing the
  (snap-only) NordVPN client. The Ubuntu base remains the default and is
  unchanged.
- The e2e suite gains `TestVMTorrentWireGuardKillSwitch`, which boots both
  bases, drops the tunnel, and probes for egress — the first test to check that
  the rules take effect rather than that the right rules were generated.
