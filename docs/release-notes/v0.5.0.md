## Highlights

**vee runs Windows on Apple Silicon.** The `windows` template now works on arm64 hosts — vee builds Windows 11 (or 10) arm64 install media on demand and drives a fully unattended install, exactly like it does on x86_64:

```sh
vee create win --template windows      # builds the win11 arm64 ISO, installs hands-free
vee ssh win                            # OpenSSH is enabled at first logon (vee / vee)
```

There is no manual ISO download and no driver fiddling: vee resolves the arm64 build through UUP dump, assembles a UEFI-only ISO in a container, and boots it on the aarch64 `virt` board with an NVMe system disk (Windows ARM64 ships the driver in-box), USB install media, and a ramfb display. NetKVM's Microsoft-signed ARM64 build is injected during install, so the guest has virtio networking from its first boot. Verified end-to-end on an M4 Max: unattended to the desktop in about ten minutes, auto-logged-in, SSH reachable.

Honest limits: Windows Server has no public arm64 media, so arm64 hosts offer `win11` and `win10` only; the guest display is 2D (use RDP for a real desktop); and virtiofs shares are not available in arm64 guests yet — upstream virtio-win ships no ARM64 guest-tools installer and its ARM64 `viofs` driver is test-signed only ([virtio-win#1337](https://github.com/virtio-win/kvm-guest-drivers-windows/issues/1337)).

**Linux guests can now run their own VMs.** `--nested` (or `nested: true` in `vm.yaml`) exposes EL2 to arm64 Linux guests, so Docker Desktop for Linux, KubeVirt, Firecracker, and plain `qemu -accel kvm` work inside them:

```sh
vee create dd --template devbox --nested
vee ssh dd -- ls /dev/kvm              # present: the guest kernel booted at EL2
```

On a Mac this needs an M3 or later on macOS 15+, and the guest kernel needs ARM nested-virt support (Fedora 41+ works where Fedora 40 did not). vee quietly handles the platform's sharp edges: HVF nested only works with Apple's in-kernel vGIC, and edk2 would hang forever at EL2 on a virtual-timer interrupt the framework never delivers (Apple FB21649319) — vee pairs `virtualization=on` with `kernel-irqchip=on` and the firmware boot-menu workaround automatically. Verified on an M4 Max: an Ubuntu 24.04 guest boots with `CPU: All CPU(s) started at EL2` and KVM initialized. macOS guests can never nest — Apple's frameworks refuse to run inside a VM.

**The QEMU bundle moves to 11.1.0-rc2.** Nested virtualization needs QEMU ≥ 11.1 under HVF, so the pinned `vee-qemu` bundle is now built from 11.1.0-rc2 for all four platforms. The rc is deliberate: upstream's 11.1.0 final is expected around mid-August 2026, and the pin moves to it the moment it ships. Nothing vee emits changed between QEMU 10.0 and 11.1 (checked against the removed/deprecated feature lists), and existing VMs run unchanged. As a side effect of fixing the bundle build for ANGLE's headers, the macOS bundle compiles its GL stack (virglrenderer 1.x) for the first time and ships `virtio-gpu-gl-pci` — whether that path is genuinely Metal-accelerated at runtime is still being validated, so treat `gpu.mode: virtio` acceleration claims on macOS with the usual suspicion until then.

### If you already use vee

- Existing VMs keep working unchanged; the new QEMU bundle is downloaded on the next start that needs it (checksum-verified, ~30 MB per platform).
- On x86_64 hosts the `windows` template behaves exactly as before (virtio disk + viostor injection, SPICE display, swtpm TPM, `win10` default).
- The virtio-win driver ISO is now pinned to 0.1.285 instead of the floating "stable" alias — the first release whose ARM64 drivers are attestation-signed, and pinning keeps installs reproducible. The first Windows create after upgrading downloads it once (~750 MB, cached).

### Windows-on-ARM specifics, for the curious

| | x86_64 hosts | arm64 hosts |
|---|---|---|
| System disk | virtio (viostor injected) | NVMe (in-box driver) |
| Install media | IDE CD-ROM | USB mass storage |
| Firmware | OVMF + Secure Boot + swtpm TPM | plain aarch64 edk2, checks bypassed |
| Display | SPICE | ramfb + RDP |
| Default version | `win10` | `win11` |

The arm64 media is mastered UEFI-only (ARM has no BIOS boot path), the Windows 11 hardware checks are bypassed with the same `LabConfig` keys the x86 flow already used — Windows ARM64 cannot bind QEMU's TPM device ([QEMU #830](https://gitlab.com/qemu-project/qemu/-/issues/830)) — and the 24H2 writable-scratch-disk install flow carries over unchanged. Details in [docs/windows-guests.md](../windows-guests.md#arm64-guests).
