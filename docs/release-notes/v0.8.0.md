## Highlights

**Linux guests on Virtualization.framework.** The `vz` backend is no longer
macOS-guests-only. A `vm.yaml` with `backend: vz` and no `macos:` section now
runs a Linux guest on Apple's hypervisor, selected at create time with
`vee create --backend vz` on any cloud-image template. The motivation is
vsock: the bundled macOS QEMU is a plain-HVF build and QEMU's vsock is
vhost-only (Linux/KVM), so a QEMU Linux guest on a macOS host can never get a
host↔guest vsock channel. Virtualization.framework provides
`VZVirtioSocketDevice` natively, so the whole `vsock-connect` /
`vsock-listen` machinery now works for Linux guests on macOS hosts. Guests
boot via `VZEFIBootLoader` with virtio-blk/net/vsock/rng, the console is
captured to `serial.log`, and the template's qcow2 overlay is flattened to
raw — the only format Virtualization.framework reads. QEMU-only devices (GPU,
TPM, virtiofs, bridge NIC, raw-device passthrough) are refused at create time
with actionable errors rather than silently dropped.

**Direct-kernel boot for `vz` Linux guests.** For minimal and appliance
images that ship no bootloader, `kernel:` / `cmdline:` / `initrd:` in
`vm.yaml` boot the guest through `VZLinuxBootLoader` — the
Virtualization.framework analog of QEMU's `-kernel` / `-append` / `-initrd`.
Kernel and initrd paths are verified at create time, and the fields are
refused on the QEMU backend and on `macos:` guests.

**`vee view --native` — a real display window for macOS guests.** The helper
now presents a `VZVirtualMachineView` window, so a macOS guest can be seen and
operated in the states Screen Sharing cannot reach: recoveryOS, the login
window, and the macOS installer. Only the process owning the
`VZVirtualMachine` can attach a display, so the window belongs to the helper.
Plain `vee view` falls back to it when the guest has no resolvable IP or
nothing answers on the Screen Sharing port. One window per VM run — AppKit
cannot restart the window's event loop once it terminates — and closing the
window leaves the VM running.

**`vee start --recovery` — one flag, per-backend mechanism.** Recovery means
something different on every guest, so the flag dispatches through
`vm.RecoveryPlan`: `vz` macOS guests start with
`startUpFromMacOSRecovery`; `vz` direct-kernel Linux guests get
`systemd.unit=rescue.target` appended to the boot cmdline; both are one-shot,
since the spec is rewritten from the config on every start. EFI/whole-disk
Linux, QEMU guests, and Windows have no launch-time hook, so those starts
proceed normally with a warning naming the real path (the bootloader menu, or
`reagentc /boottore` inside the guest) rather than a silent "recovery" that
never happened. Recovery environments run no sshd, so the CLI skips the
SSH-readiness spinner and prints how to reach the guest instead.

**`vee screenshot` — capture a guest's display to PNG.** Headless capture of a
running QEMU-backed VM via QMP `screendump`. QEMU emits PPM; vee decodes it
and encodes PNG internally, so no `sips` or ImageMagick is needed. Stdout
carries only the written file's absolute path, so it stays scriptable. The MCP
server gains `vm_screenshot`, which returns the PNG inline as image content —
an agent can look at the guest's screen directly.

**`vee resize` — grow a boot disk in place.** Previously this meant running
`qemu-img resize` by hand and hand-editing `vm.yaml`. `vee resize <name>
<size>` takes an absolute size (`60G`) or a relative grow (`+40G`); shrinking
is refused, as it would truncate the guest filesystem. It works on qcow2
(QEMU) and raw (`vz` Linux) boot disks, and follows the same stop/restart flow
as `vee move` (`--yes`, `--no-start`). Afterwards a per-OS hint explains how
the guest claims the space: cloud-init Linux does it on the next boot, Windows
gets the `Resize-Partition` one-liner, macOS the `diskutil resizeContainer`
command. `vm_resize` is available over MCP.

**Turnkey SSH for Windows guests.** The `windows` template came up
unreachable: no forwarded SSH port, no authorized keys in the guest, and no
guest-agent channel. It now sets a deterministic forwarded SSH port, writes
`administrators_authorized_keys` with the icacls lockdown sshd requires,
records the unattend-created admin account as `ssh_user`, and attaches the QGA
channel on amd64. (arm64 keeps SSH as the control path — its vioserial driver
is test-signed and cannot load, so a QGA channel would be a dead device.)
Relatedly, `vee config <name> --ssh-port N` now works after create: the port
is persisted for later starts and, on a running user-mode NAT guest, applied
live over QMP so no restart is needed.

**Two new templates.**

- **`dns-sink`** — a 512M Alpine VM running AdGuard Home as a LAN-wide DNS
  sinkhole, resolving and blocking from first boot with no setup wizard:
  DNS-over-TLS upstreams with DNSSEC, five blocklists, admin UI on `:3000`
  published over mDNS at `http://<name>.local:3000`. Bridge networking is
  required and enforced, since LAN clients cannot reach a resolver behind
  user-mode NAT. The admin password is prompted for interactively and only its
  bcrypt hash reaches the cloud-init seed; over MCP only a pre-computed hash is
  accepted, so a plaintext password never lands in a tool-call transcript.

- **`bitmagnet`** — the BitTorrent DHT crawler and indexer with its own
  PostgreSQL, behind a WireGuard kill switch. Crawling the DHT continuously
  announces the guest to the swarm, so the guarantee is that with WireGuard
  down *nothing* in the guest reaches the internet, as any user: OUTPUT policy
  is DROP and every exception is pinned rather than opened by port — the
  handshake only to the endpoint's resolved addresses, SSH replies only via
  conntrack `ESTABLISHED`, DHCP only to the broadcast address from source port
  68. With no VPN configured the crawler is disabled outright rather than
  warned about. The web UI is never exposed to the network and is reached over
  `vee tunnel`; `--pg-data-dir` bind-mounts a host directory over virtiofs so
  the index outlives the VM.

**GPL source distribution for the bundled QEMU.** Releases now satisfy GPLv2 §3
by same-place source distribution instead of a written offer: the exact
upstream `qemu-<version>.tar.xz` (with sha256), the macOS build's one-line
`egl-helpers.c` patch, and a snapshot of the build scripts, workflow, and
entitlements that produced the bundles are attached as release assets.

### If you already use vee

- `vee create --boot-disk <image>` now works. Every `--boot-disk` /
  `--data-disk` entry was hardcoded as raw passthrough, so pointing it at a
  `.qcow2` produced a VM that dropped to the UEFI shell. Paths are now
  classified: block devices pass through raw as before, regular files are
  adopted as image files with their format probed by `qemu-img info` and their
  path absolutised, and anything else is rejected at create time. An adopted
  image belongs to you, not to vee — it is never created, resized, relocated,
  or deleted by vee's disk management.
- `vee ssh -- <cmd>` against a Windows guest no longer mangles arguments.
  POSIX single-quoting was applied regardless of guest OS, but Windows' sshd
  hands the string to `cmd.exe`, which treats single quotes literally — so
  whether a command worked depended only on which characters it contained.
  Windows guests now get `cmd.exe`-compatible quoting.
- `vee ssh` into a guest whose template injects keys into the image's built-in
  account (`docker`, `desktop`, `dns-sink`) no longer logs in as your local
  host username. Username resolution is centralised in
  `VMConfig.SSHUsername()`: `ssh_user`, then the cloud-init user, then the
  distro default.
- The `windows` template now floors its system disk at 64G (Microsoft's stated
  Windows 11 minimum); the old 20G default left a fresh install with ~4 GB
  free. A larger configured `default_disk_size` still wins, and qcow2 is thin,
  so the bigger virtual size costs no host space until the guest writes.
- On Apple Silicon, `make build` and `make install` now build and install
  `vee-vz-helper` too, instead of leaving it stale unless `make vz-helper` was
  run by hand.
- `vee qmp` no longer fails outright when the daemon does not own a VM's QMP
  connection (e.g. a VM started standalone after the daemon booted); it falls
  through to a direct dial.
- Existing Windows VMs keep their stored config. Set the SSH user once with
  `vee config <name>`, or pass `--user vee`.
