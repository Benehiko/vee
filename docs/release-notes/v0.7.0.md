## Highlights

**The vee daemon now runs on macOS.** `vee daemon install` registers the
daemon with the host's native service manager on both platforms, so VMs
autostart at boot and are powered off cleanly when the host shuts down:

- **Linux — systemd.** The installer writes a system unit to
  `/etc/systemd/system/vee.service`, then enables and starts it. systemd
  starts the daemon at boot and restarts it on failure. While at least one
  VM is running, the daemon holds a systemd-logind `shutdown:sleep` block
  inhibitor; when logind broadcasts `PrepareForShutdown`, it stops every
  running VM in parallel before letting the host power off. Manage it with
  `systemctl status|restart|stop vee`.

- **macOS — launchd.** The installer writes a system-level LaunchDaemon to
  `/Library/LaunchDaemons/io.vee.daemon.plist` that runs the daemon as your
  user account, then loads and starts it with `launchctl bootstrap`.
  `RunAtLoad` starts it at boot and `KeepAlive` restarts it on failure — the
  launchd analogues of enabling the systemd unit and `Restart=on-failure`.
  macOS has no logind, so vee maps launchd's shutdown contract onto the same
  graceful path: at shutdown the daemon receives SIGTERM and has up to 300 s
  (`ExitTimeOut`) to stop every running VM cleanly before exiting. While VMs
  run it also holds a `caffeinate -i` assertion so the host never
  idle-sleeps under running guests. Check it with
  `sudo launchctl print system/io.vee.daemon`; after upgrading the binary,
  restart it with `sudo launchctl kickstart -k system/io.vee.daemon`.

A LaunchDaemon — not a per-user LaunchAgent — is used for the same reason
Linux uses a system unit: it survives logout and is still alive during host
shutdown. The Linux-only vfio, udev, and polkit install steps are skipped on
macOS. See
[docs/host-shutdown.md](https://github.com/Benehiko/vee/blob/main/docs/host-shutdown.md)
for the full shutdown story on each platform.

**Host↔guest vsock on macOS guests.** Virtualization.framework guests can
now expose a virtio socket device (`--vsock` on `vee create`, `vsock: true`
in `vm.yaml`), giving the host a private channel into a macOS guest that
does not depend on NAT networking. The helper protocol gains `vsock-connect`
(bridge a guest-listening vsock port onto a unix socket in the VM directory)
and `vsock-listen` (forward guest-initiated connections to a host unix
socket). QEMU guests keep using the existing vhost-vsock device.

**`vee network` — one command to debug VM networking.** `vee network <vm>`
reports a running VM's network state from both sides of the VM boundary:
NIC mode, ARP visibility, SSH reachability, and guest-agent availability on
the host side; interfaces, routes, DNS, firewall, VPN state, and real egress
IPs probed inside the guest. VPN-configured VMs (the torrent template) get
pass/fail checks for the kill switch, tunnel routing, and DNS leaks —
including correct handling of NordLynx/WireGuard policy routing, which never
rewrites the main routing table. `--json` emits the structured report, and
the same data is available over MCP as the read-only `vm_network` tool.

**Boot-time Resizable BAR management (`vee gpu rebar`).** A GPU bound to
vfio-pci at boot keeps its firmware-default 256M BAR0, so passthrough guests
lose ReBAR/SAM and compute stacks that map all VRAM fail allocations. Since
a BAR can only be resized with no driver bound — and RDNA3 cards do not
survive a runtime rebind — `vee gpu rebar <addr> --size 16G` installs an
mkinitcpio early hook that applies the resize in early userspace, before
vfio-pci loads. Run it without `--size` to see the current and supported BAR
sizes.

### If you already use vee

- `vee delete` (and MCP `vm_delete`) now accepts multiple VM names and
  continues past per-VM failures.
- `vee create --disk` now adds a bootable **extra** disk instead of silently
  shadowing the OS disk.
- `--verbose` now actually lowers the log level instead of only adding a log
  sink.
- Bridge-mode guests: SSH no longer dials a dead `127.0.0.1` port, guest
  discovery uses an unprivileged ARP sweep instead of a privileged broadcast
  ping, and `vee tunnel` falls back to SSH forwarding for firewalled guests.
- The torrent template got a hardening pass: the QEMU guest agent is now
  enabled, mounts persist across reboots, and NordVPN daemon access works
  for both the `vee` and default cloud-init users.
