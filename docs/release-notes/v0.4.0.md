## Highlights

**vee runs macOS guests.** On an Apple Silicon Mac, vee can now restore and drive a macOS VM through Apple's Virtualization.framework:

```sh
vee create mymac --template macos      # restore the newest macOS this host supports, then start it
vee ssh mymac                          # works on the first boot — no GUI setup needed
vee view mymac                         # the guest's screen over Screen Sharing
```

No Apple ID and no paid developer account are needed. vee asks the host which restore image it supports, downloads that IPSW (15–20 GB, cached), installs it, and then patches the guest's disk offline so the guest is usable without anyone sitting at its display: Setup Assistant is marked done, an admin account is created, your vee SSH key is authorized, and Remote Login and Screen Sharing are switched on.

**Existing QEMU VMs keep working unchanged.** The backend is a per-VM field, chosen independently of the guest OS, and a VM created before this release has no `backend:` field at all — so it resolves to QEMU exactly as before. No config migration, no new required fields.

### If you already use vee with QEMU

Three things are worth knowing, none of which require action:

- **`vee ip` now answers for bridge-mode VMs without a guest agent.** It used to fail with "was not started with guest agent support"; it now resolves the guest by MAC from the host's lease and neighbour tables and prints a bare IP, so `$(vee ip myvm)` is scriptable. User-mode (slirp) guests are unchanged — they never appear in those tables, so guessing would return nothing or a stale lease.
- **The `github-runner` journal caps and disk-GC bounds ship for the first time.** They were merged after `v0.3.5` was tagged, so this is the release that carries them.
- **Ctrl-C is handled by vee rather than by the shell.** The CLI now runs under a signal context, so an interrupt cancels the command's work and lets it unwind instead of terminating the process outright.

### Also in this release, for macOS guests

- **`vee stop` shuts a macOS guest down cleanly** instead of waiting out the grace period and killing it. macOS ignores the ACPI-powerdown equivalent, so vee asks the guest over SSH; a stop went from 30 s to about 6 s.
- **Screen Sharing works without touching System Settings.** Since macOS 12.1 the screen-sharing agent needs privacy (TCC) permissions that only System Settings or MDM can grant — neither reachable on a headless guest. vee writes them into the guest's privacy database directly, which is possible while the guest's disk is idle. Because macOS only creates that database during the guest's first boot, `vee create` restarts the guest once to complete the grant.

### What macOS guests can and cannot do

| | |
|---|---|
| Works | create / start / stop / delete / list / status, `vee ssh`, `vee ip`, `vee view`, graceful shutdown, guest-shutdown detection, autostart, `vee logs` |
| Not applicable | SPICE, `vee monitor`, `vee qmp`, dashboard stats — this backend has no SPICE server and no QMP |
| Unavailable | `vee check`, `vee ports` — they need the QEMU guest agent |
| Not implemented yet | snapshots, `vee move`, virtiofs shares, suspend/resume |

Two limits worth knowing before you start:

- **Apple's licence permits macOS VMs only on Apple hardware, and at most two at a time.** Virtualization.framework enforces the two-VM cap itself — a third macOS guest fails to start.
- **A macOS guest cannot run VMs of its own.** Virtualization.framework exposes nested virtualization only to Linux guests, and Apple states that neither Virtualization.framework nor Hypervisor.framework works from inside a VM. So Docker Desktop, Podman Machine, Lima and UTM will not start in a macOS guest. Run them on the host or in a sibling Linux guest.

**Requirements:** Apple Silicon, macOS 13 or newer, and the `vee-vz-helper` binary from the `darwin-arm64` tarball (install instructions below). Guests older than the host are fine; newer than the host is not.

Full documentation: [macOS guests](https://vee.benehiko.com/getting-started/macos-guests/).
